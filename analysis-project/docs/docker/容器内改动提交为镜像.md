# Docker 镜像更新：容器内改动如何提交为新镜像

## 场景

容器 `analysis-project-test`（镜像 `analysis-project:plan-b`）已在运行中，出于调试或依赖验证目的，直接在容器内安装了新的 pip 包（`docker exec ... pip install ...`）。现在需要把容器当前状态固化成镜像，并且**镜像名保持不变**，原镜像保留为历史版本。

> 注意：容器内手动 `pip install` 的改动只存在于容器的可写层，容器被 `docker rm` 后就丢失。所以要么 commit 成镜像，要么把依赖写进 Dockerfile 重新构建，二选一。

## 操作步骤

### 1. 给旧镜像打历史版本 tag

```bash
docker tag analysis-project:plan-b analysis-project:plan-b-backup-<日期>
# 例：
docker tag analysis-project:plan-b analysis-project:plan-b-backup-20260920
```

这一步必须在 commit 之前做。`docker commit` 会把 tag 指向新镜像，如果没有提前备份，旧镜像会变成悬空镜像（`<none>`），只能靠 IMAGE ID 找回。

### 2. 提交容器为原镜像名

```bash
docker commit analysis-project-test analysis-project:plan-b
```

- commit 是对容器可写层做快照，pip 装到 `/usr/local/lib/python*/site-packages` 的包会包含进去。
- 运行中的容器可以直接 commit（默认短暂 pause），不一定要先停容器。
- **bind mount 的目录不进镜像**：本项目的 `/workspace/harness-a2a` bind mount 到宿主机 `/java/analysis-workspace`，memory/artifacts/sessions 等内容靠宿主机目录持久化，与镜像无关。

### 3. 重启容器验证

```bash
docker restart analysis-project-test
docker ps    # 确认容器仍基于 analysis-project:plan-b
```

验证新包生效：

```bash
docker exec analysis-project-test pip list | grep <包名>
```

或直接跑一次依赖该包的功能做 E2E。

### 4. 清理历史版本（可选）

确认新镜像运行稳定后，不需要的备份可以删除：

```bash
docker rmi analysis-project:plan-b-backup-20260920
```

## 长期建议

如果新依赖是长期需要的，应把包名写进 Dockerfile（本项目 `plan-b` 镜像含 `jpype1` 等依赖，见 [[workspace_persistence_bind_mount]] 相关记录）重新 build，而不是长期依赖 `docker commit`：

- commit 的镜像没有构建历史（Dockerfile 层级），体积和可追溯性都差；
- 换机器/重建环境时无法复现。

commit 适合「临时验证 -> 固化当前状态 -> 后续再补进 Dockerfile」的过渡场景。
