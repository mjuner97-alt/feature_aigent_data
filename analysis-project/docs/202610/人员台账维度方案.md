## 2. 台账数据访问层（新 `PersonLedgerRepository`）

新 `v2/dimension/PersonLedgerRepository.java`，**JdbcTemplate(gaussCommonDataSource) 模式，
同 VersionCalendarRepository**（V2DimensionConfig.java:129 装配、TTL 快照 +
失败保陈旧），不建 MyBatis Mapper、不进 auth 包。

### 2.1 快照口径

```
统计月份 = (SELECT MAX("统计月份") FROM developer_pl_person_info_t)   -- 业务拍板：取 max 统计月份
```

与旧表/旧 Mapper 的 `版本月份` 口径**无关**（新表两列并存，业务明确按统计月份）。

### 2.2 SQL 集合（中文列名一律双引号；参数全部 PreparedStatement 绑定）

```sql
-- Q1 按统一认证号查人员归属（"我部/我组/我的应用/我的产品线/我"）
SELECT DISTINCT "部门", "统计组", "应用", "产品线", "姓名", "统一认证号"
FROM developer_pl_person_info_t
WHERE "统一认证号" = ? AND "统计月份" = (SELECT MAX("统计月份") FROM developer_pl_person_info_t)

-- Q2 按姓名查（人名识别；返回多行 = 重名/兼岗，反问或展开）
SELECT DISTINCT "部门", "统计组", "姓名", "统一认证号"
FROM developer_pl_person_info_t
WHERE "姓名" = ? AND "统计月份" = (SELECT MAX("统计月份") FROM developer_pl_person_info_t)

-- Q3 姓名字典（人名扫描用，全量缓存内存 Set）
SELECT DISTINCT "姓名" FROM developer_pl_person_info_t
WHERE "统计月份" = (SELECT MAX("统计月份") FROM developer_pl_person_info_t) AND "姓名" IS NOT NULL

-- Q4 部门下钻清单（人名单；组/应用/产品线下钻同构，换列即可）
SELECT DISTINCT "统计组", "姓名", "统一认证号" FROM developer_pl_person_info_t
WHERE "部门" = ? AND "统计月份" = (SELECT MAX("统计月份") FROM developer_pl_person_info_t)
```

注意：`nvarchar2` 在 openGauss A 兼容下**空串视为 NULL**，业务全量数据（约 2800 个
统一认证号）导入后 `应用/产品线/统计组` 大量空值是正常现象，SQL 已用 IS NOT NULL /
DISTINCT 吸收；索引 `("统一认证号","统计月份")` 已覆盖 Q1。

### 2.3 缓存

| 缓存 | 内容 | TTL | 失败降级 |
|---|---|---|---|
| per-user 归属 | Q1 结果（LinkedHashSet 保序去重） | 30min（台账月度更新，天级粒度足够） | 查不到 → 返回空（见 §3.5 降级） |
| 姓名字典 | Q3 全量姓名 Set | 30min | 加载失败 → 人名扫描整体关闭（只影响 G4，不影响其余能力） |

2800 人级别全量姓名常驻内存无压力。

## 3. 机制一：用户关系（我部/我组/我的应用/我的产品线/我）

### 3.1 口语词提取（A 类字面固定短语，代码正则，不进 dimension_key_config）

新 `v2/dimension/PersonalDimensionResolver.java`：

```java
public enum PersonalRef { MY_DEPT, MY_GROUP, MY_APP, MY_PRODUCT_LINE, MYSELF }
private static final Pattern MY_DEPT    = Pattern.compile("我部|我们部门|我的部门|本部门|我所在部门");
private static final Pattern MY_GROUP   = Pattern.compile("我的组|我们组|我的团队|我们团队|我的小组|我的统计组");
private static final Pattern MY_APP     = Pattern.compile("我的应用(群组)?");
private static final Pattern MY_PRODUCT = Pattern.compile("我的(产品线|条线|业务线)");
private static final Pattern MYSELF     = Pattern.compile("(?<![一-龥])我(们)?(个人|本人)?(?![一-龥组们的])"); // 见 §3.6 误伤约束
```

> 词表归属说明：这些是**代词结构**（随用户身份变化），不是封闭业务词表，归代码正则
> （同 杭[一二三四五]部 处理思路）；业务后续想加新说法时再评估迁 dimension_key_config
> 白名单（机制已留好，VOCAB_MERGE_KEYS 模式可平移）。

### 3.2 解析（`PersonalDimensionResolver.resolve(question, userId)`）

返回 `PersonalResolution`：

```java
record PersonalResolution(boolean myDept, boolean myGroup, boolean myApp,
                          boolean myProductLine, boolean myself,
                          PersonLedgerRow ledger /* Q1 结果, 可为 null */) {}
record PersonLedgerRow(List<String> depts, List<String> groups, List<String> apps,
                       List<String> productLines, String name, String userId) {}
```

- 任一命中且 userId 非空 → 查 Q1（缓存）；
- userId 为空 / 台账查无此人 → resolution 返回命中标志但 ledger=null（§3.5 降级）；
- 一人多行（兼岗/借调）：distinct 收集为多值。**部门/组/应用/产品线都天然支持多值**
  （deptName 是 List、PeerDimension.getValues 是 List），默认全量传入不反问（拍板点①）。

### 3.3 注入点 A：直接执行路径（主场景）—— extraction 级 enrich

`plan` 已有 userId（DirectSkillExecutor 调用处 V2ChatStreamServiceImpl.java:461）。
**主场景校准（2026-10-22）**：enrich 不经 DimensionState/PeerDimension，直接在
`extract` 产出的 `DimensionExtraction` 上填字段——param_mapping 绑哪个键就用哪个值，
这才是直接执行参数解析的正式入口：

```java
DimensionState preview = dimensionStateManager.previewState(question, previousState);
DimensionExtraction extraction = extract(preview, ...);
PersonalResolution personal = personalResolver.resolve(question, userId);   // 新增
extraction = enrichExtraction(extraction, personal);                        // 新增，见下表
// 顺序约束：我X enrich 必须在 人名扫描(§4) 与 下钻展开键(§5) 之前——
// "我部人员的缺陷数" 要先有 deptName 才能展开 perNo
```

enrich 字段映射（合并语义，显式值优先保留，去重）：

| 口语命中 | extraction 字段追加 | 查库 |
|---|---|---|
| myDept | `deptName += ledger.depts` | Q1 |
| myGroup | `groupName += ledger.groups` | Q1 |
| myApp | `appName += ledger.apps` | Q1 |
| myProduct | `productLine += ledger.productLines` | Q1 |
| myself | `perNo += [userId]`（**不查库**）；`perName += [ledger.name]`（Q1，查无跳过） | 部分 |

**关键调整：直接执行路径绕开 PeerDimension 三选一。** extraction 里
`groupName/appName/productLine` 是三个独立字段，"我的组和我的应用"双命中各自落位，
param_mapping 绑谁谁生效——原拍板点②的冲突在直接执行路径**不存在**；三选一约束只
保留在 DimensionState（LLM 回退路径）里。plan 级感知/活动键计算不受影响。

### 3.3b 注入点 B：LLM 回退路径（DimensionStateMiddleware，次要）

仅当直接执行未命中（回退 LLM 链路）时才有意义：`onSystemPrompt` 用 ctx.userId()
resolve 后写入 DimensionState（departments / peerDimension / persons，**此处维持
PeerDimension 三选一，双命中时先命中者胜 + warn**）并写回 ctx 跨轮继承，
`formatDimensionContext` 注入标准名。LLM 回退路径的注入是兜底体验，不承载参数契约。

### 3.4 新内置键 `perNo`（统一认证号）—— G3/G4 的共同承载

- `DIMENSION_KEYS` 9 → 10：加 `"perNo"`（label：统一认证号）；
- `DimensionKeyConfigRepository.BUILTIN_KEYS` 同步加 seed 行（builtin=true，aliases 空）；
- `DirectSkillExecutor.valuesFor("perNo")` → `extraction.perNo()`；
- **脚本契约**：按人的统计脚本 param_mapping 绑 `perNo`（统一认证号），展示层绑
  `perName`（姓名）。这正是业务表"个人→统一认证号"行的直接落地；
- `perNo` 值来源两个：`myself`（= ChatRequest.userId 本身，不查库）与
  人名解析（§4，查 Q2）。**执行期解析，不进 DimensionState、不进指纹**（同锚点原则
  —— 口语值方案 §3.2"解析结果绝不进指纹"）；
- **主场景定位（2026-10-22）**：perNo 本质上是为 param_mapping 而生的键（直接执行
  脚本收统一认证号）；LLM 回退路径不经此键，靠 §4.4 的 prompt 注入行。

### 3.5 降级契约（fail-safe，对齐口语值方案 §3.3）

| 场景 | 行为 |
|---|---|
| userId 为空（anonymous） | 口语命中但不注入任何维度，问题原样走 LLM（LLM 自己处理不了也不会卡死） |
| 台账查无此人 / Q1 失败 | 同上；log warn |
| "我的组"命中但 ledger.groups 为空（台账该列空） | 不注入 groupName；若这导致必填参数缺失，走既有缺参反问/回退 LLM 链路 |

### 3.6 "我"字面误伤约束

`MYSELF` 必须避免吞掉"我们组/我的部门"等复合词（命中 MY_DEPT/MY_GROUP 时不再触发
MYSELF，先查具体维度后查自身）；`我们` 单独出现（"我们部门"）由 MY_DEPT 承接，
裸"我们"不触发任何注入。

## 4. 机制二：人名识别（xxx → 统一认证号）—— G4

### 4.1 提取（字典扫描，非 NER；主战场在 plan）

规则：在 `buildMaskedQuestion`（DimensionStateManager.java:378，已屏蔽时间/部门/应用/
需求项/需求子条目 span）之后的文本上，穷举 2~4 字中文窗口（步进 1），命中姓名字典
（Q3 缓存 Set，**精确匹配**）即为姓名候选。

- **主场景校准（2026-10-22）**：扫描挂在 `DirectSkillExecutor.plan` 内（我X enrich
  之后、buildParams 之前），产物直接填 `extraction.perName/perNo`——与 §3.3 同一
  参数解析主链路，不经 DimensionState；
- 为什么字典扫描而不是正则：中文人名无结构特征，正则必海量误伤；台账字典只有
  ~2800 条，窗口穷举每问题几十次 Set.contains，成本可忽略；
- 为什么 2~4 字：台账姓名（含民族姓名常见长度）不超 4 字，窗口越界自动跳过；
- 屏蔽保证"杭州开发三部"里的"三部"不会与人名撞（且姓名字典里不会有"三部"）。

### 4.2 解析与反问（直接执行走 askMessage + pending，LLM 链路兜底）

对每个命中姓名查 Q2：

| 结果 | 行为（直接执行主场景） |
|---|---|
| 唯一统一认证号 | `extraction.perName += [姓名]`，`extraction.perNo += [统一认证号]` |
| 多个统一认证号（重名/同人兼岗多部门） | **反问**：`DirectExecutionPlan.askMessage` 下发
  「徐三金（杭州开发三部 / 杭州开发二部）」序号选择，pending 记录
  `PendingDirectExec(missingKeys=[perNo@ambiguous])`，补参轮 `consumePending` 用
  序号/部门名匹配 → perNo 落地 → 继续执行。**复用时间歧义锚点的既有 pending 机制**
  （时间维度方案 §3.3 同构，不新增状态机） |
| 同名同部门同人多行（兼岗，多个应用/组） | 统一认证号相同 → 视为唯一，合并行取值 |

**LLM 链路兜底**：直接执行未命中回退时，`startClarificationIfAmbiguous` 状态机
（DimensionStateManager.java:1447/1476）仍可承接同款反问（PendingClarification 扩
PERSON 语义位，拍板点④）——两条路各自复用既有反问基建，不新建。

### 4.3 优先级与冲突

- extraction 里 `perName/perNo` 与 `groupName/appName/productLine` 是**独立字段**，
  无结构冲突；"张三组"这类带组后缀的词由 EXPLICIT_TEAM 抢走，人名扫描只吃裸名
  （屏蔽 + 字典精确匹配双保险）；
- alias 词表命中（aliasHit）不抑制人名扫描（字段不同），但 alias 占用的 span 已被
  最长匹配消费，窗口扫描天然跳过（实现上把 alias/team/PL 命中 span 一并加入屏蔽集）；
- LLM 回退链路：DimensionPrompts 的 persons 字段语义补一句"人名须为台账姓名"，
  perNo 由注入上下文给出（§4.4）。

### 4.4 LLM 回退路径注入（DimensionStateMiddleware，次要）

`onSystemPrompt` 有 ctx（ctx.userId()）：

1. resolve 口语命中 + 人名扫描 → enrich DimensionState（departments/peer/persons）后
   写回 ctx（**跨轮继承**：下一轮"他呢？"能继承到我部）；
2. `formatDimensionContext` 增补一行：人名已解析出统一认证号时输出
   `「徐三金」→ 统一认证号 555153289（杭州开发三部）`，并加指令"涉及该人的查询参数
   perNo 请直接使用此统一认证号"。

## 5. 机制三：下钻维度 —— drillDown 动态键为主，展开键可选

> 2026-10-22 二次定稿（内网已配置 `drillDown` 动态键后重新对齐）：
> **drillDown（输出分组粒度）为主**——脚本收 `deptName + drillDown(组维度/应用维度/
> 个人维度/产品线维度/杭研维度)` 自己 GROUP BY，动态键轨开箱即用零代码；
> **§5.2 展开键（输入过滤值列表）降级为可选**——仅当脚本只能收定值数组、无法自行
> 分组时才用。两者语义不同层：drillDown 控制"怎么分组"（输出形态），展开键控制
> "过滤什么值"（输入值域）。perNo/人名 与 drillDown=个人维度 正交：
> 分组到人走 drillDown，过滤到某人（张三/我）走 perNo。

### 5.1 drillDown 动态键（已在内网 dimension_key_config 配置，非 builtin）

机制路径（现有动态键轨，无代码改动）：

1. `extractExtraDimensions`（DirectSkillExecutor.java:771-815）contains 扫描：
   "杭州三部**各组**的缺陷密度" 命中 alias「各组」→ `extraDimensions["drillDown"]=["组维度"]`；
2. param_mapping `{"deptName":"deptName","下钻维度":"drillDown"}` → `valuesFor` default
   分支原样传「组维度」给脚本；
3. 脚本按 `部门 + drillDown` 自行 GROUP BY；
4. 动态键只当前问题提取、不跨轮继承（动态维度方案 §9.1），追问"那按应用呢"重新
   命中词表，行为正确。

**已知冲突（已修，2026-10-22）——粒度词被组/产品线正则抢成垃圾 peer 值**：
`EXPLICIT_TEAM = ([一-龥A-Za-z0-9]{2,}组)`（DimensionStateManager.java）会匹配
"各个组/每个组"；`EXPLICIT_PRODUCT_LINE` 会匹配"各个产品线"。内网实证
"杭州三部10月版各组、各产品线Qi各卡口完成率" → 部门/时间 span 屏蔽后候选仅剩
"各组"（1 字前缀构不成屏蔽命中）→ **原文回退整段吞成 "杭州三部10月版各组"** →
`groupName=[杭州三部10月版各组]` → stat_group 传垃圾值查空集。
**修法（粒度词守卫，已落地 DimensionStateManager）**，三层：
① 候选首字 ∈ {各,每,按} 即拒（分组/分产品线裸词仅 1 字前缀构不成正则命中，
且真实组名有"分行业务组"形态不能拒"分"）；
② 原文回退候选在屏蔽文本上做尾巴检查——前缀全被时间/部门 span 屏蔽、露出
≤4 字粒度尾巴（"杭州三部10月版各组"）即拒；真组名含时间片段（"10月攻关组"）
露出的"攻关"非粒度前导字，不误伤；
③ `detectLevel` 的组/产品线命中判定同样改走屏蔽文本+守卫（该问句不再误判 PEER，
归 DEPARTMENT）。drillDown 词表 span 加入 `buildMaskedQuestion` 屏蔽集未做——
粒度词均以各/每/按开头，①已覆盖，暂无必要。

**第四层（尾缀守卫 hasGranularityTail，2026-10-22 本机 E2E 补）**：
内网复测实证 "我部10月版各组、Qi各卡口完成率"（userId=880000035）→
**"我部"不被 EXPLICIT_DEPT 屏蔽**（该正则只认 "杭州开发X部" 全称），时间屏蔽后
原文回退整段吞成 `groupName=["我部10月版各组"]`；候选首字是"我"，①拦不住。
修法：候选紧贴后缀（组 suffixLen=1 / 产品线 suffixLen=3）的 1~2 字 ∈ {各,每,按}
即拒（回看 2 字覆盖"各个组"/"每个产品线"——"个"字夹在中间）；
真组名尾字非粒度前导（分行业务组/个人住房组/10月三组/数据智能组）不受影响。
DimensionStateManagerRuleTest 增补：我部10月版各组/我部各组/我部各产品线/我部每个组
→ peer null；我部、数据智能组 → 数据智能组照常提取。

**第五层（词表反哺，2026-10-23 定稿实施）**：E2E 再实证 "具体到各统计组"
（粒度字藏在词中间，首字/尾缀守卫靠位置枚举永远追不出变体）。位置守卫到此为止，
**drillDown 动态键词表自动反哺为垃圾屏蔽词源**：字典里 alias value ∈ {组维度→groupName,
应用维度→appName, 产品线维度→productLine} 的粒度词（个人维度不映射——人名走台账字典
真名匹配；杭研维度不映射——deptName 正则只认杭州开发X部），原词作为 contains 屏蔽词
接入 findTeamToken/findProductLineToken/hasTeamOrProductLineHit 三处候选判定。
业务在 drillDown 词表补一条 `统计组→组维度` 即同时生效：①extractExtraDimensions
contains-scan 正确解析 `drill_down=组维度` ②所有含"统计组"的组名垃圾值被拒——
一处配置双向生效，覆盖不全由配置自愈，不用发版。
DimensionStateManagerRuleTest 再增 1 个（含词干垃圾值拒绝+层级归 DEPARTMENT+
"杭研维度"不映射不误伤真组名），全套 668 过。

**双绑 groupName/productLine 的影响（2026-10-22 与业务确认：会双绑）**：
- **守卫落地前**有真实风险："杭州三部各组的缺陷数" → drillDown=组维度 +
  **groupName=["各组"]（正则抢的粒度词垃圾值）**，脚本把 groupName 当过滤条件
  （`AND 统计组='各组'`）会查空集；"各产品线" 同理污染 productLine；
- **守卫落地后双绑合法且必要**："个人住房组各人的缺陷数" → drillDown=个人维度 +
  groupName=个人住房组（真过滤值），"过滤维度 + 分组维度"叠加是正当场景；
- 守卫零误伤已确认（拍板点⑧：业务无以 各/每/按/分 开头的真实组名）→ **守卫排 P1**，
  不留过渡期窗口；若业务在守卫上线前先配了双绑，脚本侧临时自查
  `drillDown='组维度'` 时忽略 groupName（同轴粒度优先）。

### 5.2 展开键（可选，按脚本入参形态启用）

> 降级说明：drillDown 覆盖"脚本可自行分组"的下钻场景（主路径）；以下展开键仅在
> 脚本**无法自行分组、只能收定值数组**时启用（如脚本 API 只接受 perNo 数组做 IN 过滤）。
> 未出现此类脚本前不实施。

层级关系（真源 = 台账 `_t`，快照口径 max 统计月份）：

```
部门(deptName) ⊇ 统计组(groupName) / 应用(appName) / 产品线(productLine) ⊇ 人(perNo/perName)
```

- 展开方向只**向下**（下钻），不向上（"个人住房组属于哪个部"不做——组名归属由
  维度上下文继承与脚本自身口径解决）；
- 多值输入（"一部和二部"）→ 展开取**并集**去重保序。

### 5.3 展开键契约（param_mapping 合法值扩展，activeKeys 同源）

| param_mapping value | 语义 | valuesFor 产出（执行期） |
|---|---|---|
| `deptName.groups` | 部门 → 其下统计组列表 | `["个人住房场景建设组",…]` |
| `deptName.apps` | 部门 → 其下应用列表 | `["F-GCS",…]` |
| `deptName.productLines` | 部门 → 其下产品线列表 | `["个人信贷产品线",…]` |
| `deptName.perNos` | 部门 → 其下所有人统一认证号 | `["555153289",…]` |
| `groupName.perNos` | 统计组 → 组内人统一认证号 | 同构 |
| `appName.perNos` / `productLine.perNos` | 应用/产品线 → 人员 | 同构 |
| `deptName.perNames`（可选） | 部门 → 姓名列表（展示型脚本用） | `["徐三金",…]` |

- 输入取 `extraction.deptName()/groupName()/appName()/productLine()` 的**当前值**
  （含"我部"注入的标准名，§3.3 enrich 在展开之前完成——顺序保证）；
- 展开查询走 `PersonLedgerRepository`（Q4 同构 SQL，§2.2）+ TTL 缓存；
- 失败/空集 → 返回空 → 参数不传 → 必填缺失走既有缺参反问/回退 LLM（fail-safe，
  对齐锚点降级契约）；
- **展开产物不进指纹不进状态**（同锚点原则：指纹只含原词"杭州开发三部"，台账月更
  后同问题自动取新名单）；
- 形状：展开产物恒多值，`shapeValue` 按 schema `type=array` 恒传 List（复用
  direct-exec-param-type 方案，无新逻辑）。

### 5.4 实现落点（可选能力，出现"只能收定值数组"的脚本时随 P2 实施）

- `DirectSkillExecutor.valuesFor` 加展开键 case（输入为空直接返回空，不查台账）；
- `activeKeys()` 的 `expandKeys` 链追加展开键（`VersionPlanAnchorResolver.expandKeys`
  之后串一层，或在同处一并追加），管理页 param_mapping 下拉/保存校验自动透出；
- 典型配置示例（届时业务配脚本）："三部下人员的缺陷数" → 脚本参数收
  `perNo` 数组，param_mapping `{"perNo":"deptName.perNos"}`；"个人住房组人员清单" →
  `{"perNo":"groupName.perNos"}`；
- 列举类问题（"三部下有哪些组"）不需要展开键——那是"deptName 直传 + 脚本自己
  SELECT DISTINCT"的普通 skill（旧 §5.1 设计降级为届时业务配置选项，不再本方案驱动）。

### 5.5 LLM 回退路径

不注入展开产物（大列表会撑爆 2000 字上下文预算）；维度上下文照常注入
deptName/groupName 标准名，回退链路的脚本由 LLM 按目录装配，行为与现状一致。

### 5.6 明确不做

- **不在 Java 侧新增 person_ledger 查询工具注册给子 agent**（避免工具面膨胀，与
  2026/07/26 宽表工具重构的教训一致）；
- 下钻不做多级递归展开（部门→组→人 一段 param_mapping 只展开一层；要两级就配
  两个后缀键各绑一个参数）；
- 向上归并（组→部门）。

## 6. 指纹与缓存（ResponseCache）

- persons 已进 `toCacheKey`（person=姓名），跨轮继承/指纹累计不变；
- **perNo 不进状态不进指纹**（执行期解析，同锚点拍板②）；
- **重名撞指纹风险**：同名"张三"在不同部门语义不同，但指纹只含姓名 → 两用户问
  "张三的缺陷数"可能命中同一条缓存。ResponseCache 现状是全局指纹（未含 userId）。
  两个缓解：a) 指纹段 `person=` 改为存 `姓名(统一认证号)`（解析结果进指纹，破"解析结果
  不进指纹"原则的受控例外）；或 b) ResponseCache 指纹加 userId 前缀。建议 a（影响面
  最小），拍板点③；
- 口语命中（我部/我组）短语无需绕过缓存：同一 userId 下解析结果确定性（台账月更），
  指纹含解析后的标准部门名，天然正确；**跨 userId 本就不同指纹**（注入的部门值不同）。

   "各组"）；粒度词守卫："各组/每个组/按组/分组/各产品线" 不产 TEAM/PL 值，正常组名
   （数据智能组/质量保障组）不受影响；追问"那按应用呢" 重新命中词表；
   **展开键（可选，实施时补）**：`{"perNo":"deptName.perNos"}` 收统一认证号数组；
   "一部和二部"并集去重；台账查询失败 → 参数不传 → 缺参反问/回退 LLM；
6. **缓存**：同名不同部门撞指纹场景（拍板③选 a 后不撞）；我部解析结果可缓存；
7. **回归**：全量单测基线（当前 580+）；DimensionExtraction 加字段后
