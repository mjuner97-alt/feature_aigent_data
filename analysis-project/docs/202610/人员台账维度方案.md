# 人员台账维度方案（我部/我组 · 维度下钻 · 人名识别）

> 状态：设计稿 v1（2026-10-21，未实施）。

## 2. 台账数据访问层（新 `PersonLedgerRepository`）

新 `v2/dimension/PersonLedgerRepository.java`，**JdbcTemplate(gaussCommonDataSource) 模式，
同 VersionCalendarRepository**（V2DimensionConfig.java:129 装配、TTL 快照 +
失败保陈旧），不建 MyBatis Mapper、不进 auth 包。

### 2.1 快照口径

```
统计月份 = (SELECT MAX("统计月份") FROM developer_pl_person_info_t)   -- 业务拍板：取 max 统计月份
```

与旧表/旧 Mapper 的 `版本月份` 口径**无关**（新表两列并存，业务明确按统计月份）。

### 2.2 SQL 集合（中文列名一律双引号；参数全部 PreparedStatement 绑定）

```sql
-- Q1 按统一认证号查人员归属（"我部/我组/我的应用/我的产品线/我"）
SELECT DISTINCT "部门", "统计组", "应用", "产品线", "姓名", "统一认证号"
FROM developer_pl_person_info_t
WHERE "统一认证号" = ? AND "统计月份" = (SELECT MAX("统计月份") FROM developer_pl_person_info_t)

-- Q2 按姓名查（人名识别；返回多行 = 重名/兼岗，反问或展开）
SELECT DISTINCT "部门", "统计组", "姓名", "统一认证号"
FROM developer_pl_person_info_t
WHERE "姓名" = ? AND "统计月份" = (SELECT MAX("统计月份") FROM developer_pl_person_info_t)

-- Q3 姓名字典（人名扫描用，全量缓存内存 Set）
SELECT DISTINCT "姓名" FROM developer_pl_person_info_t
WHERE "统计月份" = (SELECT MAX("统计月份") FROM developer_pl_person_info_t) AND "姓名" IS NOT NULL

-- Q4 部门下钻清单（人名单；组/应用/产品线下钻同构，换列即可）
SELECT DISTINCT "统计组", "姓名", "统一认证号" FROM developer_pl_person_info_t
WHERE "部门" = ? AND "统计月份" = (SELECT MAX("统计月份") FROM developer_pl_person_info_t)
```

注意：`nvarchar2` 在 openGauss A 兼容下**空串视为 NULL**，业务全量数据（约 2800 个
统一认证号）导入后 `应用/产品线/统计组` 大量空值是正常现象，SQL 已用 IS NOT NULL /
DISTINCT 吸收；索引 `("统一认证号","统计月份")` 已覆盖 Q1。

### 2.3 缓存

| 缓存 | 内容 | TTL | 失败降级 |
|---|---|---|---|
| per-user 归属 | Q1 结果（LinkedHashSet 保序去重） | 30min（台账月度更新，天级粒度足够） | 查不到 → 返回空（见 §3.5 降级） |
| 姓名字典 | Q3 全量姓名 Set | 30min | 加载失败 → 人名扫描整体关闭（只影响 G4，不影响其余能力） |

2800 人级别全量姓名常驻内存无压力。

## 3. 机制一：用户关系（我部/我组/我的应用/我的产品线/我）

### 3.1 口语词提取（A 类字面固定短语，代码正则，不进 dimension_key_config）

新 `v2/dimension/PersonalDimensionResolver.java`：

```java
public enum PersonalRef { MY_DEPT, MY_GROUP, MY_APP, MY_PRODUCT_LINE, MYSELF }
private static final Pattern MY_DEPT    = Pattern.compile("我部|我们部门|我的部门|本部门|我所在部门");
private static final Pattern MY_GROUP   = Pattern.compile("我的组|我们组|我的团队|我们团队|我的小组|我的统计组");
private static final Pattern MY_APP     = Pattern.compile("我的应用(群组)?");
private static final Pattern MY_PRODUCT = Pattern.compile("我的(产品线|条线|业务线)");
private static final Pattern MYSELF     = Pattern.compile("(?<![一-龥])我(们)?(个人|本人)?(?![一-龥组们的])"); // 见 §3.6 误伤约束
```

> 词表归属说明：这些是**代词结构**（随用户身份变化），不是封闭业务词表，归代码正则
> （同 杭[一二三四五]部 处理思路）；业务后续想加新说法时再评估迁 dimension_key_config
> 白名单（机制已留好，VOCAB_MERGE_KEYS 模式可平移）。

### 3.2 解析（`PersonalDimensionResolver.resolve(question, userId)`）

返回 `PersonalResolution`：

```java
record PersonalResolution(boolean myDept, boolean myGroup, boolean myApp,
                          boolean myProductLine, boolean myself,
                          PersonLedgerRow ledger /* Q1 结果, 可为 null */) {}
record PersonLedgerRow(List<String> depts, List<String> groups, List<String> apps,
                       List<String> productLines, String name, String userId) {}
```

- 任一命中且 userId 非空 → 查 Q1（缓存）；
- userId 为空 / 台账查无此人 → resolution 返回命中标志但 ledger=null（§3.5 降级）；
- 一人多行（兼岗/借调）：distinct 收集为多值。**部门/组/应用/产品线都天然支持多值**
  （deptName 是 List、PeerDimension.getValues 是 List），默认全量传入不反问（拍板点①）。

### 3.3 注入点 A：直接执行路径（DirectSkillExecutor.plan）

`plan` 已有 userId（DirectSkillExecutor 调用处 V2ChatStreamServiceImpl.java:461），
在 `previewState` 之后、`extract` 之前加一步 enrich：

```java
DimensionState preview = dimensionStateManager.previewState(question, previousState);
PersonalResolution personal = personalResolver.resolve(question, userId);   // 新增
// enrich 规则（合并语义，显式值优先保留，去重）：
//   myDept    → preview.departments      += ledger.depts
//   myGroup   → peerDimension(TEAM)      += ledger.groups      （peer 为空或已是 TEAM 时）
//   myApp     → peerDimension(APPLICATION) += ledger.apps
//   myProduct → peerDimension(PRODUCT_LINE) += ledger.productLines
//   myself    → persons += [ledger.name]；perNo += [userId]（见 §3.4）
```

peer 三选一冲突：peerDimension 已是异类型且 myGroup/myApp/myProduct 同时命中时
（如"我的应用和我的产品线比"），peer 只能装一个——超出部分记 warn 丢弃，拍板点②
（不建议为此扩 PeerDimension 结构）。

### 3.4 新内置键 `perNo`（统一认证号）—— G3/G4 的共同承载

- `DIMENSION_KEYS` 9 → 10：加 `"perNo"`（label：统一认证号）；
- `DimensionKeyConfigRepository.BUILTIN_KEYS` 同步加 seed 行（builtin=true，aliases 空）；
- `DirectSkillExecutor.valuesFor("perNo")` → `extraction.perNo()`；
- **脚本契约**：按人的统计脚本 param_mapping 绑 `perNo`（统一认证号），展示层绑
  `perName`（姓名）。这正是业务表"个人→统一认证号"行的直接落地；
- `perNo` 值来源两个：`myself`（= ChatRequest.userId 本身，不查库）与
  人名解析（§4，查 Q2）。**执行期解析，不进 DimensionState、不进指纹**（同锚点原则
  —— 口语值方案 §3.2"解析结果绝不进指纹"）。

### 3.5 降级契约（fail-safe，对齐口语值方案 §3.3）

| 场景 | 行为 |
|---|---|
| userId 为空（anonymous） | 口语命中但不注入任何维度，问题原样走 LLM（LLM 自己处理不了也不会卡死） |
| 台账查无此人 / Q1 失败 | 同上；log warn |
| "我的组"命中但 ledger.groups 为空（台账该列空） | 不注入 groupName；若这导致必填参数缺失，走既有缺参反问/回退 LLM 链路 |

### 3.6 "我"字面误伤约束

`MYSELF` 必须避免吞掉"我们组/我的部门"等复合词（命中 MY_DEPT/MY_GROUP 时不再触发
MYSELF，先查具体维度后查自身）；`我们` 单独出现（"我们部门"）由 MY_DEPT 承接，
裸"我们"不触发任何注入。

## 4. 机制二：人名识别（xxx → 统一认证号）—— G4

### 4.1 提取（字典扫描，非 NER）

规则：在 `buildMaskedQuestion`（DimensionStateManager.java:378，已屏蔽时间/部门/应用/
需求项/需求子条目 span）之后的文本上，穷举 2~4 字中文窗口（步进 1），命中姓名字典
（Q3 缓存 Set，**精确匹配**）即为 persons 候选。

- 为什么字典扫描而不是正则：中文人名无结构特征，正则必海量误伤；台账字典只有
  ~2800 条，窗口穷举每问题几十次 Set.contains，成本可忽略；
- 为什么 2~4 字：台账姓名（含民族姓名常见长度）不超 4 字，窗口越界自动跳过；
- 屏蔽保证"杭州开发三部"里的"三部"不会与人名撞（且姓名字典里不会有"三部"）。

### 4.2 解析与反问（复用既有反问状态机）

对每个命中姓名查 Q2：

| 结果 | 行为 |
|---|---|
| 唯一统一认证号 | `persons += [姓名]`，`perNo += [统一认证号]` |
| 多个统一认证号（重名/同人兼岗多部门） | **反问**：列出「姓名（部门 A / 部门 B）」序号选择，复用
  `startClarificationIfAmbiguous` 文本协议与 `consumeClarification` 序号匹配
  （DimensionStateManager.java:1447/1476）。`PendingClarification.dimension` 是
  PeerDimensionType 枚举，扩一个 `PERSON` 语义位或旁路一个 pending 槽（拍板点④） |
| 同名同部门同人多行（兼岗，多个应用/组） | 统一认证号相同 → 视为唯一，合并行取值 |

### 4.3 优先级与冲突

- persons 是独立槽位，与 peerDimension（组/应用/产品线）**无结构冲突**；"张三组"这类
  带组后缀的词由 EXPLICIT_TEAM 抢走，人名扫描只吃裸名（屏蔽 + 字典精确匹配双保险）；
- alias 词表命中（aliasHit）不抑制人名扫描（两者槽位不同），但 alias 占用的 span 已被
  最长匹配消费，窗口扫描天然跳过（实现上把 alias/team/PL 命中 span 一并加入屏蔽集）；
- LLM 路径（回退链路）：DimensionPrompts 的 persons 字段语义补一句"人名须为台账姓名"，
  perNo 由注入上下文给出（§4.4）。

### 4.4 LLM 路径注入（DimensionStateMiddleware）

`onSystemPrompt` 有 ctx（ctx.userId()）：

1. resolve 口语命中 + 人名扫描 → enrich DimensionState（departments/peer/persons）后
   写回 ctx（**跨轮继承**：下一轮"他呢？"能继承到我部）；
2. `formatDimensionContext` 增补一行：人名已解析出统一认证号时输出
   `「徐三金」→ 统一认证号 555153289（杭州开发三部）`，并加指令"涉及该人的查询参数
   perNo 请直接使用此统一认证号"。

## 5. 机制三：维度下钻（三部下的组/应用/产品线、人）—— G5

**拍板：下钻走"配置型 skill + 脚本"承载，不新建后端查询工具。**
理由：与 `wide_table_query 直接暴露`/`tool_routing_cutover` 的架构方向一致——业务查询
形态收敛在 script_registry/skill 配置层，Java 侧只补维度解析与传参能力（本文 §2-§4）。

### 5.1 skill/脚本配置（业务侧配置，方案给契约）

| 项 | 值 |
|---|---|
| skill 名称（建议） | 组织下钻查询（或按业务命名拆 4 个） |
| script_id | 新脚本 `person_ledger_drill`（gauss JDBC 同既有 q2_1 模式，_sql_registry.py） |
| params_schema | `drillType: string(enum: group/app/productLine/person)`、`deptName: string`、
  `groupName: string`(可选)、`appName: string`(可选)、`productLine: string`(可选) |
| param_mapping | `{"drillType":"drillType(固定值由 4 个 skill 行各配一个)"...}` —— 见下 |

建议配置 4 个 skill 行（同一脚本，drillType 各配固定值），检索词按维度分级配置：

| skill | param_mapping | 典型问题 |
|---|---|---|
| 三部下的统计组 | `{"deptName":"deptName","drillType":"drillType"}`（drillType 恒 group） | 三部下有哪些组 |
| 三部下的应用 | 同上（app） | 三部有哪些应用/产品 |
| 三部下的产品线 | 同上（productLine） | 三部下有哪些产品线 |
| 三部的人名单 | 同上（person），可加 `{"groupName":"groupName"}` 二级过滤 | 三部下个人住房组有哪些人 |

- deptName 提取已完备（EXPLICIT_DEPT + normalizeDepartment 十四别名 + 杭X 极简形），
  "三部" → 杭州开发三部 与台账 `部门` 列值域一致（建表数据已验证）；
- "XX统计组" 识别走 EXPLICIT_TEAM + alias 词表（已有），groupName 作为二级过滤参数；
- LLM 回退路径：DimensionStateMiddleware 注入部门标准名 + skill 检索命中即可，无需额外注入。

### 5.2 明确不做

- **不在 Java 侧新增 person_ledger 查询工具注册给子 agent**（避免工具面膨胀，与
  2026/07/26 宽表工具重构的教训一致）；
- 下钻不做多级递归（部门→组→人 一次一层，靠多轮追问继承，.DimensionState 已支持）。

## 6. 指纹与缓存（ResponseCache）

- persons 已进 `toCacheKey`（person=姓名），跨轮继承/指纹累计不变；
- **perNo 不进状态不进指纹**（执行期解析，同锚点拍板②）；
- **重名撞指纹风险**：同名"张三"在不同部门语义不同，但指纹只含姓名 → 两用户问
  "张三的缺陷数"可能命中同一条缓存。ResponseCache 现状是全局指纹（未含 userId）。
  两个缓解：a) 指纹段 `person=` 改为存 `姓名(统一认证号)`（解析结果进指纹，破"解析结果
  不进指纹"原则的受控例外）；或 b) ResponseCache 指纹加 userId 前缀。建议 a（影响面
  最小），拍板点③；
