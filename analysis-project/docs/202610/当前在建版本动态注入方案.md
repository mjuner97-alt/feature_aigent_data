# 当前在建版本动态注入方案（KNOWLEDGE.md 版本计划实时化）

日期：2026-10-13
状态：已实施（2026-10-13，dev gauss 建表+模拟数据落地，7 单测通过；内网 E2E 待验）

实施落点：
- `v2/hooks/VersionPlanKnowledgeHook.java`（SQL 常量 + TTL 缓存 + 注入）
- `V2SkillConfig.versionPlanKnowledgeHook` bean（gauss-common 数据源，`harness.knowledge.version-plan.enabled` / `cache-ttl-seconds`）
- `HarnessAgentPartsConfig.harnessHooks` 挂载（priority=-45）
- `KNOWLEDGE.md` 第 4 行动态优先措辞
- 本目录：`rdc_train_calendar_ddl_seed.sql`（建表+模拟数据）、`rdc_train_calendar_verify.sql`（SQL 验证）、`rdc_train_calendar_encoding_check.sql`、`RdcTrainCalendarSeed.java`（JDBC 执行器，classpath 用 gsdb/opengauss-jdbc-5.1.0.jar，pg 官方驱动缺 SCRAM 依赖连不上 openGauss）

## 1. 背景与目标

`src/main/resources/workspace/knowledge/KNOWLEDGE.md` 第 4 行：

```
● 版本计划（versionPlan）：标准格式为'xxxx年x月份版本'，例如：2026年6月份版本。当前版本（当前在建版本）默认：2026年6月份版本。
```

"当前在建版本"是写死的静态值，随时间推移会失真（现在已经落后于真实火车计划）。

目标：从 `rdc_train_calendar`（openGauss，火车日历表）用已有 SQL 实时算出**当前在建版本**（`版本计划` 字段），注入到 LLM 的领域知识中，替代写死的默认值。

## 2. 现状链路（约束）

| 环节 | 位置 | 行为 |
|---|---|---|
| WorkspaceMaterializer | `v2/config/WorkspaceMaterializer.java` | 启动时 `knowledge/` 前缀**每次从 classpath 强制覆盖**到 workspace（ALWAYS_OVERWRITE_PREFIXES） |
| WorkspaceContextHook | JAR 内部，不可改 | 每次请求把 `knowledge/` 全量注入 system prompt（`<domain_knowledge_context>`） |
| KnowledgeRetrievalHook | `v2/hooks/KnowledgeRetrievalHook.java`，priority=-40 | 仅 `knowledge-dynamic/` 按关键词按需注入（`<domain_knowledge_dynamic>`） |
| Hook 挂载点 | `v2/config/HarnessAgentPartsConfig.harnessHooks()` | 主 agent 与子 agent 共用 hooks 列表 |
| Gauss 数据源 | `spring.datasource.hikari.gauss-common`（`GaussCommonConfig`，pg driver 连 openGauss） | 可直接 JdbcTemplate 查询 |

关键约束：

1. **不能直接改 workspace 里的 KNOWLEDGE.md 当永久修改** —— 下次启动会被 classpath 覆盖打回。源头必须改 `src/main/resources` 下的源文件。
2. WorkspaceContextHook 在 JAR 内部，改不了它的注入内容；我们只能**追加**（PreCallEvent.appendSystemContent）。
3. Hook 注入必须永不阻塞请求（同 KnowledgeRetrievalHook 原则：异常 catch + log warn）。

## 3. 方案对比

### 方案 A：启动时 patch workspace 的 KNOWLEDGE.md ❌

启动后跑一个 CommandLineRunner，把 DB 查出的版本号替换进 workspace 文件第 4 行。

- 优点：LLM 只看到一个知识来源，无双源打架。
- 缺点：
  - **JVM 长跑会 stale**：跨投产日（版本切换）后不重启就一直是旧值 —— 和现在的静态写死是同一个病，只是发作更慢。
  - 要精确处理与 WorkspaceMaterializer 的时序（必须晚于 materialize），以及 bind mount 环境下文件被外部改动的并发问题。

### 方案 B：运行时 Hook + TTL 缓存注入 ✅（推荐）

新增 `VersionPlanKnowledgeHook`（PreCallEvent, priority=-45），每次请求前检查缓存，过期则查 DB 刷新，将结果以独立标签追加到 system prompt。

- 优点：跨投产日自动切换，无需重启；失败静默降级；与现有 KnowledgeRetrievalHook 模式完全一致。
- 缺点：LLM 会看到两个版本来源（KNOWLEDGE.md 静态默认 + 动态注入），需按 §5 调整 KNOWLEDGE.md 措辞声明优先级。

## 4. 方案 B 详细设计

### 4.1 SQL

沿用用户提供 SQL（openGauss 方言，gauss-common 数据源可执行）。SQL 窗口（最近投产日 ± 前后各一档，且火车开始时间 <= 今天）内会返回**多个** `版本计划` 值（例如：2026年9月份版本、2026年10月份版本、2026年11月份版本），全部注入，按 `投产日_Date` 升序去重后以"、"拼接。

SQL 全文以 Java 文本块常量存放在 Hook 类内（该 SQL 是本 hook 专属逻辑，不进 `_sql_registry.py` —— 那是 script_exec 子 agent 用的注册表）。

### 4.2 新类 `v2/hooks/VersionPlanKnowledgeHook.java`

```
职责：PreCallEvent 时注入"当前在建版本"，TTL 缓存，永不阻塞请求
priority：-45（在 KnowledgeRetrievalHook(-40) 之前跑）
依赖：GaussCommonConfig 提供的 DataSource（构造注入 JdbcTemplate）
```

核心逻辑：

```java
// 伪代码
private volatile CachedValue cache;   // (version, expireAtMillis)

onEvent(PreCallEvent e):
    if (!enabled) return;
    try {
        List<String> versions = getVersions();   // 缓存未过期直接返回；过期则 synchronized 单飞刷新
        if (!versions.isEmpty()) {
            String joined = String.join("、", versions);   // 例：2026年9月份版本、2026年10月份版本、2026年11月份版本
            e.appendSystemContent("""
                \n\n<domain_knowledge_current_version>\n
                当前在建版本（当前版本计划，实时从火车日历计算，按投产时间先后排列）：%s\n
                </domain_knowledge_current_version>\n
                """.formatted(joined));
        }
    } catch (Exception ex) {
        log.warn("VersionPlanKnowledgeHook skipped: {}", ex.getMessage());  // 静态默认兜底
    }
```

缓存与降级语义：

- TTL 默认 **1800s**（版本切换粒度是"投产日"，分钟级缓存绰绰有余），可配。
- 刷新失败 → 保留上一次成功值直到过期；从无成功值 → 不注入，KNOWLEDGE.md 静态默认兜底。
- 结果去重（`LinkedHashSet` 保序）后拼接；`版本计划` 为 NULL/空白的行跳过（openGauss `''` 视为 NULL 的历史坑）。
- 刷新用 `synchronized` + double-check，避免并发请求打爆 DB（单条主键式查询，压力本身可忽略）。
- 注入与否不依赖用户问题关键词 —— 版本计划是全场景默认值，必须始终生效。

### 4.2.1 当前在建季度推算（2026-10-13 追加）

季度不需要查库：由版本值在 Java 侧确定性推算（`(\d{4})年(\d{1,2})月份版本` → 月份 `(m-1)/3+1` 季度，如 2026年10月份版本 → 2026年4季度）。与版本行同放一个 `<domain_knowledge_current_version>` 块（KNOWLEDGE.md 第 5 行引用同一标签）：

```
<domain_knowledge_current_version>
当前在建版本（当前版本计划，实时从火车日历计算，按投产时间先后排列）：2026年9月份版本、2026年10月份版本、2026年11月份版本
当前在建季度（由在建版本推算，可能为多个，按投产时间先后排列）：2026年3季度、2026年4季度
</domain_knowledge_current_version>
```

推算去重保序；无法解析的版本值跳过季度行；全部无法解析则不输出季度行。

### 4.3 接线

1. `V2SkillConfig`：新增 `@Bean VersionPlanKnowledgeHook`，参数 `harness.knowledge.version-plan.enabled`（默认 true）、`harness.knowledge.version-plan.cache-ttl-seconds`（默认 1800），DataSource 取 gauss-common。
2. `HarnessAgentPartsConfig.harnessHooks()`：`ObjectProvider<VersionPlanKnowledgeHook>` → hooks.add，log 一行 wiring 信息（照抄 KnowledgeRetrievalHook 的写法）。

### 4.4 KNOWLEDGE.md 源文件同步修改

第 4 行改为（避免双源打架，声明动态优先）：

```
● 版本计划（versionPlan）：标准格式为'xxxx年x月份版本'，例如：2026年6月份版本。当前在建版本（可能为多个，按投产时间先后）以系统注入的 <domain_knowledge_current_version> 为准；若系统未注入，才使用默认值：2026年6月份版本。
```

### 4.5 配置项汇总

```properties
# application.properties（默认注释掉，走代码默认值）
harness.knowledge.version-plan.enabled=true
harness.knowledge.version-plan.cache-ttl-seconds=1800
```

## 5. 测试计划

- 单测（仿 KnowledgeRetrievalHook 现有测试风格）：
  1. DB 返回多行（9月/10月/11月版本）→ 注入 `<domain_knowledge_current_version>`，内容为"、"拼接的有序去重列表，并附推算季度行（2026年3季度、2026年4季度）；
  2. DB 返回 1 行 → 单值注入 + 对应季度行；
  3. TTL 内第二次调用不再查 DB（JdbcTemplate 调用计数）；
  4. 查询抛异常 → 不注入、不抛出（PreCall 正常继续）；
  5. 空结果/全部 NULL/空白字符串 → 不注入；
  6. enabled=false → 短路；
  7. 季度推算：非标准格式/null/空白版本值跳过，跨年（2027年1月份版本 → 2027年1季度）正确。
- E2E（内网，连真实 124.160.247.195 gauss）：
  1. 启动日志出现 `VersionPlanKnowledgeHook wired`；
  2. 问一个涉版本计划的问题，trace/日志确认注入块出现且值 = SQL 直查结果一致；
  3. 手工把表中常规投产日改到明天，等 TTL 过期后新请求返回新版本（验证跨投产日切换）。

## 6. 风险与开放问题

| # | 风险/问题 | 处置 |
|---|---|---|
| 1 | `rdc_train_calendar` 是否在 gauss-common 连的库（postgres@124.160.247.195）？ | 实施前先手工跑一遍 SQL 确认；不在则改挂 gauss-customer 或对应库 |
| 2 | openGauss `''` 视为 NULL（历史坑） | 只取 `版本计划` 单列，若为 NULL 跳过该行走下一行 |
| 3 | CURRENT_DATE 时区 | openGauss 服务器时区与业务一致（现状 SQL 已在生产使用），不额外处理 |
| 4 | SQL 返回多行时取哪些值 | 窗口内全部 `版本计划` 值，按 `投产日_Date` 升序去重后"、"拼接注入（例：2026年9月份版本、2026年10月份版本、2026年11月份版本） |
| 5 | 双源打架（静态默认 vs 动态注入） | §4.4 措辞声明动态优先 |

已确认的决策（2026-10-13）：

1. 注入窗口内**全部**版本值（多值列表），不是单值。
2. 该 SQL 仅供后端 hook 使用，**不**登记 `_sql_registry.py`。
