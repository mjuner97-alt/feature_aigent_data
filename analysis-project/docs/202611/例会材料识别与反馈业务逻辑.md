# 例会材料识别与反馈业务逻辑

更新日期：2026-11-18

本文整理例会材料从 PPT 导入、页面识别、部门匹配、经办分派，到部门反馈和邮件通知的业务逻辑，作为后续实现和评审依据。本文不表示相关设计均已在代码中实现。

## 反馈督办范围

- 首次待反馈通知和逾期提醒以事项的责任部门匹配督办人。经办人仍是收件人，同一人同时是经办人和督办人时只出现在收件人中。
- 督办人可负责多个部门。人员所属部门来自人员台账，督办部门在反馈督办人配置中指定。没有匹配督办人的部门照常发给经办人。
- 发布前在应用使用的 GaussDB 库和 schema 执行 [V20261120.1 迁移](../../src/main/resources/db/migration/gauss/V20261120.1__ppt_feedback_supervisor_departments.sql)。旧名单保留，未配置督办部门的人在分配部门前不参与抄送。

## 1. 已明确的业务原则

1. 标题识别优先确定页面标题、板块及适用的经办人配置；找不到标题时才从正文辅助判断。
2. 部门匹配扫描整页的标题、正文、表格及组合文本，根据“关键词 → 部门”生成异常反馈事项。
3. 从该标题确认的经办人中，选出对应部门的人员；缺少经办人也保留事项，标记为待分派。
4. 导入确认时保存识别和分派结果；后续通知、反馈记录及汇总读取保存的数据，不重新识别 PPT。
5. 联系人和经办人是不同角色：联系人是板块有问题时找的协调人，相当于板块管理员；经办人是具体负责填写反馈的人。
6. 关键词识别出的待反馈事项，通过邮件通知经办人。
7. 同一责任部门内的人员不受经办人名单限制，可以协作填写和修改反馈。
8. 部门反馈完成后，支持根据配置手动选择需要通知的人。
9. 经办人配置可能不完整，也可能通过规则匹配；后续可能调整经办人，也可能调整责任部门。

## 2. 角色及职责

| 角色 | 职责 | 主要关联范围 |
| --- | --- | --- |
| 板块联系人 | 板块出现问题时的协调入口，协调归属、配置和经办分派 | 板块 |
| 经办人 | 被指定负责填写具体事项反馈，接收待反馈通知 | 标题、部门及具体事项 |
| 责任部门成员 | 可以协作填写、代填和修改本部门事项 | 当前责任部门 |
| 实际填写人 | 实际提交或修改某次反馈的人，记录在操作历史中 | 每次反馈操作 |
| 结果通知接收人 | 在反馈完成后接收结果，可区分收件人和抄送人 | 结果通知配置及具体发送记录 |
| 材料管理人员 | 处理导入确认、识别缺口及必要的人工调整 | 材料批次、版本 |

同一个人可以兼任多个角色，但这些关系应分别配置和保存。

联系人不因协调职责自动成为经办人；其他部门成员代填，也不自动替换指定经办人。联系人或结果接收人的身份，不自动授予跨部门编辑权限。

例如：事项属于数据产品部，指定张三经办，李四代填，王五是板块联系人。事项完成后，仍应分别显示张三为经办人、李四为实际填写人、王五为板块联系人。

## 3. 业务对象及反馈粒度

```text
材料批次
  └─ 材料版本
       └─ 页面：标题、板块、文本及识别依据
            └─ 部门反馈事项
                 ├─ 当前责任部门
                 ├─ 零个或多个指定经办人
                 ├─ 部门共享的当前反馈
                 ├─ 反馈修改历史及实际操作人
                 ├─ 部门和经办人调整历史
                 └─ 通知任务及发送历史

板块 ── 板块联系人
结果通知配置 ── 默认收件人、抄送人
```

建议延续“每个版本、每页、每个命中部门一条反馈事项”的粒度。同部门多位经办人共享事项和反馈状态，不按经办人人数重复创建事项。

同页同部门多次命中关键词，可以合并为一条事项，但应保存全部命中证据。若未来需要逐条异常分别处理，再单独扩展异常明细粒度。

反馈进度按部门事项计算，不按邮件接收人数计算。

## 4. 完整流程

```text
上传 PPT
  ↓
识别页面标题、板块；必要时从正文辅助判断标题
  ↓
关联板块联系人及标题适用的经办人配置
  ↓
扫描整页关键词，生成各部门候选异常反馈事项
  ↓
按标题、部门及匹配规则确定经办人
  ↓
导入确认：核对页面、部门、经办人和配置缺口
  ↓
保存正式事项、识别依据及初始分派快照
  ↓
发布待反馈事项，通知经办人
  ├─ 缺少经办人：保留待分派事项，交由联系人或材料管理人员协调
  └─ 有经办人：发送待反馈邮件
  ↓
经办人或同部门成员填写反馈，记录实际操作人
  ↓
部门完成反馈
  ↓
按结果通知配置，手动选择收件人和抄送人并发送
```

### 4.1 标题识别与部门识别独立执行

标题用于定位页面、板块及经办规则范围。标题识别成功后，仍须扫描正文、表格及组合文本中的部门关键词。

关键词命中表示需要部门核实的候选异常，不代表已由部门确认异常。最终判断由反馈结果确定。

### 4.2 缺配与未识别的区别

| 情况 | 处理原则 |
| --- | --- |
| 标题无法识别 | 保存页面及候选依据，提示人工确认，不直接等同于无异常 |
| 未命中部门关键词 | 与识别失败、人工跳过区分，保留识别结果 |
| 部门明确但缺少经办人 | 保留正式事项，标记待分派，不因缺人丢失事项 |
| 缺少板块联系人 | 暴露配置缺口，由材料管理人员协调，不丢失事项 |
| 选择跳过页面 | 保存人工跳过及原因，与无异常区分 |

建议允许经办人缺配时确认导入。页面显示“待分派（缺少经办人）”，方便后续补齐。

## 5. 经办人匹配规则

以下优先级为建议方案，具体规则需要结合真实配置场景确定，不作为已经实现的能力：

1. 当前事项人工指定的经办人。
2. 标题与责任部门专属经办人。
3. 板块与责任部门默认经办人。
4. 部门默认经办人（明确启用后才使用）。
5. 无匹配结果，保留待分派事项。

如果同一标题、同一部门还需要按业务内容分派，可扩展为“标题＋责任部门＋业务关键词 → 经办人”。

规则应明确多条命中时采用合并还是互斥。建议初期采用同级规则合并去重、人工指定优先，不直接将整个部门所有人员作为兜底经办人。

每次确定经办人时，保存实际人员名单、匹配来源、规则标识或版本、匹配时间及是否人工覆盖。规则可变，已发生的匹配事实保留。

板块联系人是协调入口，不应作为未经明确配置的自动经办兜底。

## 6. 联系人与经办人的调整

| 调整类型 | 对事项及反馈的影响 | 后续处理 |
| --- | --- | --- |
| 更换板块联系人 | 不改变责任部门、经办人及已有反馈 | 后续协调使用当前有效联系人，历史保留 |
| 同部门增加经办人 | 保持原事项及反馈 | 按需通知新增人员 |
| 同部门移除或替换经办人 | 保留事项及反馈，不因换人重置完成状态 | 新通知使用更新后的名单 |
| 经办人离职、停用或调岗 | 原事项部门不随人员自动变化 | 标记人员有效性问题，协调替换或补齐 |
| 责任部门从 A 转交 B | 属于责任归属变化 | 记录转交；A 的反馈保留历史，建议 B 重新反馈 |

人员调岗时，当前编辑权限依据当前部门身份判断。该人员过去提交的反馈、署名及邮件历史仍保留。

若部门转交后希望继承旧反馈，应采用明确操作并记录依据，不能默认把 A 的反馈算成 B 已完成。

## 7. 全局配置与存量事项

默认配置用于生成新材料或新事项的初始安排；事项当前经办人用于实际办理。两者应分别保存。

建议修改全局经办人配置时提供明确的应用范围：

- 仅用于后续导入。
- 补齐选定未完成事项中缺失的经办人。
- 替换选定未完成事项的经办人。

应用到存量事项前展示影响范围，应用后记录调整前后名单、操作人和时间。不得因查询页面或发送邮件而静默重算并覆盖人工分派。

账号是否有效、是否仍属于责任部门，需要根据当前人员信息校验。初始快照不能代替当前有效性检查。

## 8. 反馈与权限

1. 经办人表示明确安排谁办理；同部门成员可以代填和协作修改。
2. 每个部门事项共享一份当前反馈，不为每个经办人保存独立完成状态。
3. 保存实际提交人、修改人、时间、反馈内容及附件历史。
4. 代填不自动改变指定经办人。
5. 缺少经办人不应阻止有权限的部门成员反馈。
6. 同部门多人并发编辑时，应通过修订号检查避免无提示覆盖。
7. 编辑权限依据当前身份、当前责任部门及业务状态判断；联系人身份和邮件接收身份不直接等于编辑权限。

## 9. 两类邮件通知

| 类型 | 目的 | 默认接收对象 | 触发方式 |
| --- | --- | --- | --- |
| 待反馈通知 | 提醒处理候选异常事项 | 事项当前经办人 | 发布、补充分派或明确补发 |
| 反馈结果通知 | 告知部门反馈结果 | 单独配置的结果收件人、抄送人 | 手动发送 |

两套名单分别维护。同一人负责多条事项时，可以按材料版本及部门汇总，收件人去重，并记录邮件覆盖的事项范围。

缺少经办人的事项，应向联系人或材料管理人员暴露待协调任务；是否额外自动发送协调邮件属于后续产品选择，不默认已经启用。

补齐经办人后，对仍需反馈的事项按需补发。已经反馈完成的事项，不因补人自动再次发送催办邮件。

结果通知默认名单可以长期保存，本次发送可以临时调整；临时调整不必自动回写默认配置。是否允许跨部门接收结果，需要与查看权限分别确定。

建议结果通知关联“材料版本＋部门＋发送时反馈修订”。发送后反馈发生变化，显示“反馈已更新，尚未通知最新结果”，由用户决定是否再次发送。

如果支持未全部完成时发送阶段结果，应明确标注完成进度，避免误认为全部完成。

邮件发送历史保存当时实际使用的收件人、抄送人、地址、主题、正文或内容快照、关联事项及反馈修订、操作人、时间和发送状态。即使默认名单变化，历史记录也不改写。

建议待发送任务先持久化，再由后台发送和重试。重试需要控制重复发送；接口已受理与实际投递成功应按邮件服务可提供的状态分别记录。

## 10. 持久化边界

持久化表示数据可保存、可追溯，不意味着所有字段不可修改。应区分默认配置、初始快照、当前业务状态和历史事件。

| 数据 | 保存方式 | 更新原则 |
| --- | --- | --- |
| 原始 PPT、文件摘要、材料版本 | 持久化来源文件及版本信息 | 新上传形成独立版本 |
| 确认标题、板块、页面文本及识别依据 | 持久化识别结果 | 人工修正留痕，不在展示时重新识别 |
| 部门命中关键词、原文及规则依据 | 持久化证据 | 后续配置变化不改写历史证据 |
| 板块默认联系人 | 持久化可维护配置 | 后续协调使用当前有效配置 |
| 导入时板块联系人、经办人和部门 | 持久化初始快照 | 用于追溯，不覆盖当前安排 |
| 当前责任部门及经办人 | 持久化当前业务关系 | 允许明确调整，保存变更历史 |
| 经办人规则和默认通知名单 | 持久化配置 | 可维护，保存版本或审计记录 |
| 当前反馈、附件及修改历史 | 持久化业务记录 | 记录实际操作人，与经办人分开 |
| 通知任务及每次实际发送记录 | 持久化事件 | 默认配置变化不得覆盖历史 |
| 用户当前部门、账号有效性 | 可以同步或缓存 | 权限及发送前使用当前有效信息 |
| 是否具有编辑权限 | 不保存为永久不变的结论 | 依据当前身份、归属和状态计算 |
| 完成率、待分派数量、待通知数量 | 通常从业务数据计算，可缓存 | 以事项及历史记录为准 |
| 导入前的候选识别结果 | 可临时保存 | 未确认前不作为正式反馈任务 |

后续读取逻辑：

- 反馈页面读取正式事项、当前经办关系及已保存反馈。
- 待反馈邮件读取当前有效经办关系，并保存本次实际收件快照。
- 历史页面读取历史事件及当时快照。
- 权限校验读取当前有效的部门身份。
- 上述过程均不重新解析 PPT 来决定事项和部门。

## 11. 状态建议

建议将不同维度分开表达，避免一个状态同时承担归属、分派、反馈和通知含义：

| 维度 | 示例状态 |
| --- | --- |
| 部门归属 | 待确认、已确认 |
| 经办分派 | 待分派、已分派、存在失效经办人 |
| 反馈办理 | 待反馈、已确认异常、已判定非异常 |
| 待反馈通知 | 未发送、发送中、成功、失败 |
| 结果通知 | 未发送、已发送当前修订、反馈已更新 |

例如，事项可以同时是“已反馈＋待分派”：部门成员已代填，但尚未补齐指定经办人。不应因此清空反馈或重复计算待反馈任务。

## 12. 与现有实现的衔接及后续事项

此前代码检查可见，项目已有导入时保存事项和经办人快照、按部门校验编辑权限、记录分派调整、保存通知默认名单和邮件记录的基础。

后续实现应重点核对：

1. 标题完全没有经办人时，当前存在阻止导入确认的校验，应与缺配也保留事项的原则统一。
2. 人工调整接口目前要求目标部门至少一位经办人，应核对是否支持调整后暂时待分派。
3. 明确板块联系人独立于标题经办人，不能用一套名单混合表达。
4. 当前按页、按部门生成事项时，应补齐多次命中的证据保存。
5. 明确全局规则变更应用到存量事项的范围，避免隐式覆盖。
6. 将待反馈通知与反馈结果通知的业务含义、默认名单和历史记录区分。
7. 结果通知当前存在默认名单限本部门人员的实现限制，若需跨部门通知应另行调整，并单独判断查看权限。
8. 检查后台通知任务的持久化与失败重试，避免仅依赖进程内调度。

以下细节尚需结合具体使用场景确定，本文只提供建议：经办规则实际优先级及冲突策略、联系人协调邮件是否自动发送、结果通知是否允许阶段发送及跨部门收件、部门转交后的反馈继承方式。

## 13. 典型业务示例

某版本第 5 页识别为“业务运行情况”，属于运营板块，板块联系人为王五。整页命中数据产品部和杭州产品部关键词。

1. 生成两条部门事项，分别归数据产品部和杭州产品部。
2. 数据产品部匹配经办人张三；杭州产品部没有匹配经办人，保留待分派。
3. 导入确认后保存上述结果，通知张三，并向协调入口展示杭州产品部缺配情况。
4. 数据产品部李四代为填写，记录经办人为张三、实际填写人为李四，事项计为已反馈。
5. 王五协调补齐杭州产品部经办人赵六，对尚需反馈的事项补发通知。
6. 后续张三被同部门陈七替换，保留李四的反馈和原通知记录，不重置完成状态。
7. 部门完成反馈后，用户按结果通知配置手动选择收件人和抄送人发送邮件，保存当次反馈修订与发送快照。
8. 后续默认经办配置改变，不自动覆盖本版本安排；如需应用到存量事项，执行明确调整并留痕。
