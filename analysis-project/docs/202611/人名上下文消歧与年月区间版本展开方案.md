# 人名上下文消歧 与 年月区间版本展开 方案

> 2026/11/23 立项，当日实施完成（7 拍板全齐；单测全绿，内网 E2E 待验）。来源 E2E 案例：
> 「看下杭州三部个贷消费组杨阳2026年缺陷密度的变化情况，从2026年6月到2026年12月」
>
> 问题①：「杨阳」在台账中 4 条重名，但问题里已给出 部门（杭州开发三部）+ 组（个贷消费场景组），
> 足以唯一锁定「杨阳（杭州开发三部 / 个贷消费场景组 / 应用开发）」，却仍然整轮反问序号。
> 问题②：「2026年6月到2026年12月」仅产出两端端点版本 `["2026年6月份版本", "2026年12月份版本"]`，
> 缺 7~11 月的逐月展开。

---

## 1. 问题① 人名重名反问未利用已知维度上下文消歧

### 1.1 现状机制（代码锚点）

人名扫描与重名反问全链路（`DirectSkillExecutor.java`）：

| 环节 | 位置 | 行为 |
|---|---|---|
| 人名扫描 | `applyPersonalDimensions` :2185-2209 | `resolver.resolveName(name)` 返回台账身份列表；`size()==1` 直填 perName/perNo；`size()>1` 记 `ambiguousName` + 全量 `candidates` |
| 反问挂起（3 处） | :739-756（multi-exec 公共段）、:968-983（单执行轨）、:1251-1262（追问层） | `pending.put` 只存 `PERSON_MARKER_PREFIX + name` 标记，**不存候选清单** |
| 答复消费 | `consumePersonPending` :2674-2706 | 重新 `resolveName(name)` 取**全量**列表 → `matchPersonReply`（序号/认证号/部门组名包含匹配 :2733-2766） |
| 反问文案 | `personAskMessage` :2771-2780 | 序号 + `displaySuffix()`（部门 / 组 / 角色） |

`PersonLedgerRepository.PersonIdentity`（PersonLedgerRepository.java:109）自带
`depts()` / `groups()` / `apps()` / `productLines()` / `roles()` —— 消歧所需上下文**已经存在**，
只是扫描处（:2205 `else if (ambiguousName == null)`）拿到多身份后**原样全量反问**，
没有拿 `extraction` 里本轮已提取（或快照继承）的 deptName/groupName/appName/productLine 做过滤。

### 1.2 方案：扫描处按已知维度过滤候选

**改动点：`applyPersonalDimensions` :2187-2209 的多身份分支。**

过滤谓词（按维度轴配对，不做交叉）：

```
候选命中 ⟺ (∃ d ∈ identity.depts()  ∩ extraction.deptName())
         ∨ (∃ g ∈ identity.groups() ∩ extraction.groupName())
```

- 匹配方式：**精确等于**（trim 后）。台账与维度词表同源标准值（部门走 `normalizeDepartment`
  归一口径，组走 alias 标准值），不做 contains 模糊，避免「杭州开发一部」误配
  「杭州开发十一部」型前缀撞车。
- perRole **不参与**过滤（本案例 4 个候选角色全是「应用开发」，无区分度；且拍板口径只提
  部门/产品线/应用/统计组四轴）。
- **实施修正（2026/11/23 编码时发现）**：台账身份 `PersonIdentity` 只有
  depts/groups/roles 三字段（`resolveName` 的 Q2 查询只查 部门/统计组/岗位角色 列，
  PersonLedgerRepository.java:109），应用/产品线两轴**无从比对**，实际过滤轴收敛为
  **部门+组** 两轴。本案例正是 部门+组 双轴，不受影响。

过滤后三态：

1. **剩 1 个** → 视同唯一命中：走既有 `withResolvedPerson`（:2708）路径直填
   perName/perNo/perRole，不挂 pending，不反问，直接进入后续执行。日志
   `人名 X 重名 N → 上下文消歧命中 1 (dept=..., group=...)`。
2. **剩 0 个** → 上下文与台账不一致（提取值可能被真值校验消解或有误），**保留全量候选**
   走原反问链路（宁可多问，不可猜错）。
3. **剩 2~N 个** → 反问，但**只展示过滤后候选**（`personAskMessage` 传过滤清单）。

### 1.3 关键坑：pending 不存候选 → 序号错位

`consumePersonPending` :2680 重新 `resolveName(name)` 取**全量**列表做序号匹配。
一旦反问展示的是过滤后子集，用户回复「1」会按全量列表的序号取人 —— 错位选错人。

**修法**：`PendingDirectExec`（:405-409）加一个可空字段：

```java
record PendingDirectExec(..., List<String> pendingAnchors,
                         List<PersonLedgerRepository.PersonIdentity> pendingCandidates) {}
```

- 3 处人名反问挂 pending 时传入 `personScan.candidates()`（即过滤后清单）；
  其余场景（时间锚点歧义/缺参补参）传 `null`，兼容既有构造器（`pendingOf` :411 补默认 null）。
- `consumePersonPending` :2680 改为：`pendingCandidates` 非空用之，为空回退
  `resolveName(name)`（兼容跨版本残留的旧 pending，语义不变）。

由于过滤发生在 `applyPersonalDimensions`（公共段 :710 一次），multi-exec / 单执行轨 /
追问层三个反问点自动同口径，无需各自重复过滤。

### 1.4 时序注意

过滤用的是 :710 时刻的 `base`（truthScan 之后、重锚抑制 :713 之前）——
此时提取体里既有本轮显式值，也含快照继承值。追问轮「杨阳的缺陷密度呢」继承上轮
deptName/groupName 时同样能消歧，是期望行为；抑制在扫描之后跑，不影响过滤输入。

### 1.5 附带发现（本方案不修，留观察）

复现 trace 中 `extraction.extraDimensions.noVersion = ["2"]`：反问答复轮的裸「2」被
`extractExtraDimensions`（动态维度词表扫描）收成了某个动态键的值。本轮因
param_mapping 无对应键未落入 params，无实害；但裸序号答复被词表误吸的通路值得后续
核查（答复轮 question 建议先过序号匹配再进动态维度扫描，或对纯数字短答复屏蔽词表扫描）。
（2026/11/23 拍板：暂时不管。）

### 1.6 问题③ 会话内已确认的人名，后续轮仍重复反问

**现象**：同一会话内，用户对「杨阳」答复序号确认过一次；后续再问「杨阳xxx指标」，
`applyPersonalDimensions` 重新 `resolveName` 拿到全量候选，再次整轮反问。

**现状机制**：`consumePersonPending`（:2701）确认后只把 perNo 落进**本次** params +
`recordLastExec` 快照；确认结果没有会话级落点，下一轮扫描完全不知道上轮选过谁。

**方案：会话级人名确认登记表（钉定）**

- 存储：`confirmedPersons = ConcurrentHashMap<sessionKey, Map<name, PersonIdentity>>`，
  与 `pending` 同 sessionKey 口径（同文件内存态）。
- **写入点**：`consumePersonPending` `matchPersonReply` 成功后
  `confirmedPersons.computeIfAbsent(key).put(name, chosen)`；反问轮用户换选（答复命中
  另一候选）覆盖旧值。
- **读取/裁决顺序**（叠加在 §1.2 上下文过滤之上，`applyPersonalDimensions` 多身份分支）：

```
filtered = 上下文过滤（§1.2 四轴）
filtered ≥ 1:  pinned ∈ filtered → 用 pinned（不再问）
               filtered == 1     → 用 filtered（显式上下文换人，如「杭州二部的杨阳」）
               否则              → 反问（过滤清单）
filtered == 0: pinned ∈ 当前全量候选 → 用 pinned（本轮无显式上下文，沿用已确认身份）
               否则                  → 全量反问
```

- pinned 使用前校验其仍在 `resolveName` 当前列表内（防台账变动后脏 perNo 直填）。
- 生命周期口径：内存态、不跨会话（换 conversationId 重新反问）、不跨重启（重启后该
  会话再提重名会再反问一次并重新钉定，与 `pending` 同款口径）；条目极小无需 TTL。
- **钉定写入点补充（裁决走查发现的缺口）**：除反问答复外，**任何一轮以非反问方式确定
  唯一身份**（§1.2 上下文过滤直填 / 台账本就唯一）也刷新钉定 —— 否则显式换人后下一轮
  无上下文提问会退回旧人。

**裁决走查示例（同一会话连续 5 轮，候选同 §首案例 4 条「杨阳」）**：

| 轮 | 提问 | filtered（四轴过滤） | pinned | 结果 | 钉定变化 |
|---|---|---|---|---|---|
| 1 | 「杭州三部个贷消费组杨阳…缺陷密度」 | [2号·三部/个贷] | 无 | filtered==1 → **直填 2号**，不反问 | pinned=2号 |
| 2 | 「杨阳12月版本的缺陷密度呢」 | []（无显式部门/组） | 2号 | filtered==0 → pinned ∈ 全量 → **直填 2号**，不反问 | 不变 |
| 3 | 「杭州二部GPC组杨阳的缺陷呢」 | [4号·二部/GPC] | 2号 | filtered==1 且 ≠pinned → **直填 4号**（显式换人，钉定不阻塞） | pinned=**4号**（唯一命中刷新钉定） |
| 4 | 「杨阳的质量呢」 | [] | 4号 | filtered==0 → pinned ∈ 全量 → **直填 4号**（跟的是上一轮换的人，不是最初的 2号） | 不变 |
| 5 | 「杭州五部杨阳…」（该部门下有 2 个杨阳） | [两个候选] | 4号∉filtered | filtered>1 → **反问**（只列 filtered 2 项），答复后 pinned 更新为答复者 | pinned=答复者 |

对照组（若无钉定机制，即现状）：轮 2 和轮 4 都会再弹一次 4 选 1 反问。
若轮 3 换人不刷新钉定（缺补充规则时）：轮 4 会退回 2号 —— 与用户意图（刚切到 4号）相反。

跨会话对照：另开新会话问「杨阳的缺陷密度」→ 无显式上下文且无钉定 → 全量反问（拍板⑦口径）。

## 2. 问题② 「2026年6月到2026年12月」未做逐月版本展开

### 2.1 现状机制（代码锚点）

版本区间展开目前只有一种形态（`DimensionStateManager.java`）：

- `RANGE_VERSION` :353-354：`YEAR_PREFIX (\d{1,2}) [-~～—至到] (\d{1,2}) 月份?…`
  —— 只匹配 **「6到12月」**（月后缀仅在末段），命中后 `addRangeValues`（:1082）逐月展开。
- 用户口语 **「6月到12月」**（两侧都带「月」）不在其内：
  两端分别被 `EXPLICIT_VERSION` :331（`\d{1,2}月份?(?!延后)版本?`，版本后缀可选）
  各吃成单值 → `["2026年6月份版本", "2026年12月份版本"]`，中段丢失。
- 单数正则收端点时无「该 span 已被区间语义占用」的概念，因为区间正则根本没命中。

### 2.2 方案：新增两侧带「月」的区间正则

**新增 `RANGE_VERSION_MONTH`**（与 `RANGE_VERSION` 同构，月后缀两侧各一个）：

```java
// "6月到12月" / "2026年6月到2026年12月" / "2026年11月到2027年2月"：两侧带月后缀的
// 月份闭区间 → 逐月版本。第二端可自带年份前缀（跨年），缺省继承第一端年份。
// (?!\s*\d{1,2}[日号]) 防第二端是裸日期尾部（"6月到12月26日" 是日期区间，归日期轨）
private static final Pattern RANGE_VERSION_MONTH = Pattern.compile(
        YEAR_PREFIX + "(\\d{1,2})月\\s*[-~～—至到]\\s*" + YEAR_PREFIX
                + "(\\d{1,2})月(?!\\s*\\d{1,2}[日号])");
```

要点：

1. **接入位置**：`extractExplicitDimensions` 中紧随既有 `RANGE_VERSION` 块（:1079-1084）
   之后、`EXPLICIT_VERSION` 单数正则之前；span 并入 `sharedTimeSpans` 屏蔽集，
   防 `EXPLICIT_VERSION`/`EXPLICIT_MONTH` 从两端重复收值（与既有区间口径一致）。
2. **展开语义**：从 (年1,月1) 到 (年2,月2) 逐月步进，产出 `{y}年{m}月份版本`。
   - 第二端年份缺省 → 继承**第一端**年份（不是当前年）：「2026年6月到12月」→ 2026年6~12月；
     「6月到12月」（全裸）→ 两端补当前年（与 `yearOf` 口径一致）。
   - 跨年支持：「2026年11月到2027年2月」→ 11/12/1/2 四个月版本。
   - **同月/倒序弃收**：归一后 end < start（含两端同年 start>end）整段弃收，不产出
     （与 `addRangeValues` 既有「start>end 弃收」口径一致）。
   - **上限护栏**：展开跨度 > 24 个月整段弃收并打 warn（防病态输入撑爆 params）。
3. **日期轨不抢**：
   - 第一端后必须紧跟分隔符（`\s*[-至到]`）——「6月26日到7月1日」在「6月」处因后随
     数字不匹配；「26日到…」处数字后无「月」也不匹配。
   - 第二端 `(?!\s*\d{1,2}[日号])` 挡「6月到12月26日」型混合形态——该形态维持现状走
     日期轨（`TimeRangeExtractor.absoluteDateSpans` / MIXED_RANGE），本方案不接管。
   - 回归口径：既有 `dateShieldSpans`（:741）先跑，裸日期「10月26日」已被屏蔽，
     「11月版、12月版10月26日到期」型历史案例不受影响（新正则首端「12月」后随
     「10月26日到期」中的「10」——不是分隔符，天然不匹配）。
4. **语义拍板（默认口径）**：「X年X月到X年X月」（纯年月、无日）在该业务域归 **版本域**
   逐月展开，不归 DATE 时间范围轨 —— 与「1-3季度」「10-12月份版本」的既有展开语义对齐。
   若将来需要真正的按日查询区间，应由用户显式带「日」（走日期轨），不靠本正则猜。
5. **指纹/缓存影响**：展开后 versionPlan 多值化（本案例 2→7 值），auto-synth 指纹与
   上轮不同属预期变化；`shapeValue` 保形（array 恒传 List，10/20 拍板）无需改动。

### 2.3 语义示例：版本轨 vs 日期轨（拍板点 3 说明）

系统里时间有两条轨：**版本轨**（versionPlan，脚本收到一组「X年X月份版本」，逐版本各出
一个值，适合「变化情况/趋势」类问题）和**日期轨**（timeRange，脚本收到一个
start~end 日期区间做汇总过滤，适合「某几天合计」类问题，**必须显式带「日」**）。

| 输入 | 轨 | 产出 | 说明 |
|---|---|---|---|
| 「从2026年6月到2026年12月」 | 版本轨 | `versionPlan = [6月版, 7月版, 8月版, 9月版, 10月版, 11月版, 12月版]` 共 7 值 | **本方案新增**：现状只有两端 2 值，缺中段 |
| 「6月到12月」 | 版本轨 | 同上（补当前年） | 本方案新增 |
| 「2026年11月到2027年2月」 | 版本轨 | 11月/12月/1月/2月版 共 4 值 | 跨年，本方案新增 |
| 「10-12月份版本」「1-3季度」 | 版本轨 | 逐月/逐季展开 | **既有行为**，本次只是把「6月到12月」形态对齐到同一语义 |
| 「9月28日到9月30日的缺陷数」 | 日期轨 | `timeRange = DATE:2026-09-28~2026-09-30` | 带「日」→ 日期轨，**本方案不接管、维持现状** |
| 「6月26日到7月1日」 | 日期轨 | 日期区间 | 带「日」，不动 |
| 「6月到12月26日」（混合） | 日期轨 | 日期区间 | 末段带「日」，正则负环视挡住不展开，维持现状 |

直观对比（同一问题两种语义的差异）：

- 「看下**2026年6月到2026年12月**缺陷密度的**变化情况**」
  → 版本轨：返回 7 行，每月一行缺陷密度 → 能看趋势 ✅（本方案口径）
  → 若走日期轨：返回 1 行，6/1~12/31 整段汇总值 → 看不了趋势 ❌
- 「统计**6月26日到7月1日**的缺陷**总数**」
  → 日期轨：按日区间过滤合计 ✅（维持现状，不归版本轨）

判定规则一句话：**纯年月区间（两端都没有「日」）→ 版本域逐月展开；任一端带「日」→ 日期轨**。
与既有「10-12月份版本」「1-3季度」的展开语义完全对齐，只是补齐了「6月到12月」这种
两侧带月的口语形态。

### 2.4 不做的

- 不引入 `MONTH_SPAN@y1-m1~y2-m2` 锚点延迟解析（年度转版本锚点是 12 个月整年场景，
  区间展开值数量小、无日历缺位问题，inline 展开即可，避免锚点在
  VersionPlanAnchorResolver 渲染期再解析一层的复杂度）。
- 不动「近N月」「LAST:N」轨（各有专门方案）。
- 不处理「6月份到12月份版本」之外的新形态变体（如「上半年到下半年」），留需求驱动。

## 4. 测试计划

**单测（问题①）**
- 4 重名 + 问题含部门+组 → 唯一命中，无反问，perNo 直填 =「2」号身份。
- 4 重名 + 问题仅含部门（组缺）→ 过滤后仍多选 → 反问只列过滤后候选。
- 4 重名 + 回复「1」→ 按**过滤后清单**序号取人（不错位到全量列表）。
