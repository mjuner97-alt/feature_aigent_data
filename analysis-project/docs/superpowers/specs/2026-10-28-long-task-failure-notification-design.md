# 长任务失败通知分流设计

## 目标

长任务执行成功时继续向现有配置的业务收件人发送成功通知；只要存在一个或多个失败节点，就阻止成功通知，改为通知本次实际触发人和所有失败 Python 节点的创建人，并保留现有手动重跑能力。

## 现状与约束

项目已有长任务执行记录、节点执行结果、通知配置、脚本创建人字段和成功通知正文中的任务创建人联系人信息。任务创建人联系人和联系方式必须沿用成功通知的现有读取与渲染规则。

## 行为设计

1. 执行完成后汇总所有节点的最终状态。
2. 全部节点成功时，沿用现有成功通知收件人、正文和发送流程。
3. 存在失败节点时：
   - 不发送现有成功通知，也不发送给业务收件人；
   - 收集每个失败 Python 节点对应脚本的创建人；
   - 将本次实际触发人 `triggerUserId` 加入收件人集合；
   - 按用户 ID 去重，避免同一用户收到重复邮件；
   - 发送失败通知，正文包含任务、执行、失败节点和错误摘要；
   - 正文底部复用成功通知中的任务创建人联系人和联系方式；
   - 执行记录保持失败状态，修复后通过现有手动重跑入口重新执行。
4. 如果触发人同时也是任务创建人或失败脚本创建人，只保留一个收件人地址。
5. 如果失败节点创建人无法解析，不能因此把业务收件人加入失败通知；记录可诊断日志，并至少通知实际触发人。
6. 失败通知自身发送失败时，记录发送错误，不改变原始长任务失败状态，也不触发成功通知。

## 数据流与边界

执行编排层负责判定成功/失败并传递失败节点标识；通知服务负责根据脚本维护数据解析创建人、合并去重收件人、渲染失败正文并发送。成功通知路径不改变，联系人信息继续使用现有成功通知的统一来源和快照规则。

## 测试范围

覆盖全部成功、单节点失败、多节点失败、多个失败节点属于同一创建人、触发人与脚本创建人重复、创建人缺失、失败通知发送异常，以及失败后手动重跑仍可用。验证失败场景不会调用成功业务收件人发送路径，并验证联系人和联系方式出现在失败通知正文底部。

## 不在范围内

不新增审批流、不改变脚本维护表结构、不改变手动重跑语义、不重新设计成功通知模板或业务收件人配置页面。
