# 可配置时间窗口方案与校验

## 结论

推荐“固定值 + 可配置时间规则 + 预设快捷模板”。用户直接选择周期、数量、含不含当前周期、格式和排序；近 3/4/5 个月仅修改数量，不新增字典项。现有预设和 `$rule` 引用继续兼容。

2026-10-14 已实施：共用参数界面、版本化解析、HTTP 预览、业务日期试跑、保存/复制校验和缓存版本均已接入。47 项前端测试、39 项后端隔离测试通过。输出形状由脚本 schema 决定，单周期参数只能生成一项；未来或混合窗口自动显示实际偏移，避免被误标为“最近”。

## 现状证据

`ScriptParamRuleService.computeValue` 已按 `periodUnit + offsetStart + offsetEnd + formatPattern` 计算窗口。数据库中预置 `version.recent_3_months` 和 `version.recent_6_months`，但没有参数化的 N。前端 `ruleMarker` 只保存 `$rule` 和 ruleKey，不能覆盖数量或窗口。因此现有模式下，新增不同 N 确实需要新字典规则。

流程执行快照已保存 `scriptParamsJson` 和 `dataDate`，解析后的参数已参与缓存 key；这些可以复用。工作区 Python 脚本同时存在月份版本列表和 `start_date/end_date` 查询，二者必须保持不同输出语义。

## 方案比较

| 方案 | 优点 | 局限 |
| --- | --- | --- |
| 为每个组合新增预设 | 修改最少，继续旧机制 | 数量、周期、格式、排序组合不断膨胀 |
| 给字典引用附加 count 等覆盖字段 | 初期实现较小 | 引用仍依赖可变字典；多个覆盖字段与偏移窗口容易矛盾 |
| 将结构化时间配置保存在节点，预设仅作快捷填充 | 任意 N、可预览、可校验，配置可快照 | 需要扩展参数编辑器和解析/校验服务 |

第三种最适合本项目。第一版无需表达式语言或脚本求值，也不扩展任意上下文变量、上游节点引用和业务日历。

## 用户操作

参数取值模式为“固定值”和“动态时间”。动态时间提供：

- 周期：月、季度、年。
- 窗口：最近 N 个周期；明确“含当前周期”或“最近 N 个完整周期”。新配置推荐默认完整周期，已有预设保持原有含当前周期的语义。
- 输出：周期列表或单个周期。单个周期只允许一个结果；不从列表自动取第一项、拼接或丢弃值。
- 格式：提供 `YYYY-MM`、`YYYYMM`、中文月份版本等快捷选项，以及受限占位符格式。
- 顺序：从旧到新或从新到旧。
- 预览：明确显示基准数据日期、实际结果数量和全部结果（长列表可折叠）。

“近 3 个月”“近 4 个月”“近 5 个月”修改 N 即可。高级配置可用起止偏移表达前后周期窗口，但不与 N 同时作为独立持久化字段。

## 规范配置

```json
{
  "version": {
    "$dynamic": {
      "v": 1,
      "kind": "period_window",
      "unit": "month",
      "startOffset": -4,
      "endOffset": 0,
      "format": "{year}年{month}月份版本",
      "order": "asc",
      "output": "list"
    }
  }
}
```

此配置表示含当前月的近 5 个月。将 UI 的 N 转成偏移：含当前周期为 `startOffset=1-N,endOffset=0`；完整周期为 `startOffset=-N,endOffset=-1`。不同时保存 count、includeCurrent 和偏移，避免冲突。

新选择的预设复制其完整配置到节点；更改字典模板不追溯覆盖已保存节点。旧 `$rule` 保持旧行为，不强制迁移。`v` 为解析器语义版本，后续升级不能改变既有版本的含义。

## 核心约束

1. 时间锚点使用任务执行快照的 `dataDate`，同一任务的所有节点、重试使用同一日期。预览与试跑调用同一后端解析器，并显式显示基准日期；需要指定日期时传入相同解析上下文。业务时区统一为系统配置，不能由执行机器时区隐式决定。
2. 用 Java `YearMonth`、`LocalDate` 做周期运算，避免将一个月当作 30 天，或从月末直接递减导致语义混乱。
3. 列表仅绑定兼容元素类型的数组参数；单周期仅绑定兼容字符串/日期等明确支持类型。数字和布尔类型不默认提供字符串周期规则。数组改成字符串后必须拒绝不兼容配置，而非自动截断。
4. `output=list` 即使只有一项仍输出数组；`output=single` 必须恰好一项。结果形式不随 N 自动变化。
5. 保存、模板保存/启用、正式执行、试跑都做服务端校验：版本、字段白名单、周期、整数偏移、窗口顺序、最大数量、格式占位符、输出基数和脚本 schema 类型。缺失/非法 schema 不能按兼容模式静默放行新动态配置。
6. 建议第一版最大生成 120 项，这是可配置产品限制，不能理解为业务已有硬限制；零、负数数量、小数、超限窗口拒绝。
7. 格式只支持经过校验的占位符和普通文本，不执行 Python、JavaScript、SQL 或任意表达式。
8. 保存原始配置；执行日志同时保留基准日期和实际解析值。解析结果继续参与现有缓存 key，解析器版本也应纳入稳定的缓存语义。
9. 普通参数规范化必须保留 `$dynamic` 和旧 `$rule`；不得再次发生对象转字符串的问题。

## 日期范围边界

“月份版本列表”与“近 N 个月的数据查询区间”不是同一种输出。现有使用 `start_date/end_date` 的脚本应提供独立的日期范围配置并显式绑定两个字段，不将列表拼成字符串。范围须约定月历窗口/滚动时间、含不含当月，以及闭区间/半开区间。第一版先完成周期参数化；日期范围作为同一解析服务的后续明确类型，不能隐含自动转换。

## 校验结果与限度

在 Node 中执行了独立方案模型校验：3 个年份（含闰年）、12 个月、月/季度/年、7 种数量（含 3/4/5 和 120）、含当前/完整周期、正序/倒序，共 3024 组；对照 UTC 日历运算验证结果、数量和去重，全部通过。另验证跨年和非法数量。

| 基准数据日期 | 配置 | 预期结果（YYYY-MM） |
| --- | --- | --- |
| 2026-10-14 | 近 3 个月，含当月 | 2026-08、2026-09、2026-10 |
| 2026-10-14 | 近 4 个月，含当月 | 2026-07 至 2026-10 |
| 2026-10-14 | 近 5 个月，含当月 | 2026-06 至 2026-10 |
| 2026-10-14 | 最近 3 个完整月 | 2026-07、2026-08、2026-09 |
| 2026-01-14 | 近 3 个月，含当月 | 2025-11、2025-12、2026-01 |

这些结果验证了窗口模型，不代表尚未编写的生产实现已通过测试。实施时还必须做 Java 解析与类型校验测试、模板/长任务保存和复制测试、预览与正式执行一致性测试、重试跨月测试和旧 `$rule` 兼容测试。
