# 团队通知配置实施计划

目标为跨部门添加团队、独立维护每个团队的收件人和抄送人、按团队分页及展开两行名单。

## 数据与接口

- [x] 扩展原通知人员表，以 record_kind 区分团队配置及人员记录，回填团队配置并支持空名单。
- [x] 增加团队分页、批量保存、删除接口，继续使用现有通知人员表保存有序名单。
- [x] 事务保存整批团队，校验重复团队及人员，使用版本号防止覆盖并发修改。
- [x] 兼容原人员接口及原报告候选读取，禁止写入任务配置或任务参数池。

## 页面

- [x] 主列表每团队一条记录，展开收件人与抄送人两行，按团队搜索和分页。
- [x] 新增支持部门切换与多团队草稿，编辑回显完整名单。
- [x] 复用 MailRecipientDialog 搜索、批量添加、排序及通知类型切换，适配团队保存提示。

## 验证

- [x] 补充跨部门归属、名单顺序、重复校验、空名单与并发冲突回归测试。
- [x] 运行后端定向测试、前端交互回归测试、构建和修改文件 lint。
- [x] 审查数据库写入范围及历史兼容性，修复存量通知对默认配置的依赖。

## 验证结果

前端相关回归 16 项通过，后端回归 20 项通过，包含原表迁移及记录类型隔离回归。前端生产构建成功，626 个后端主源文件通过临时 classpath 编译，38 条 MyBatis 映射解析成功。浏览器模拟数据验证了展开名单、添加团队、跨部门选人、确认及保存刷新，并修复了窄屏弹窗溢出。

## 原表调整

根据用户要求，团队配置统一保存到 long_task_report_notify_person。迁移仅修改原表结构，新增 record_kind 和 version。历史记录默认 PERSON，按部门和团队在同表回填 TEAM 记录。TEAM 的姓名、账号、通知类型为空，enabled 固定 FALSE。数据库约束和查询条件保证 TEAM 与通知人员分别处理。人员名单清空后仍保留该团队的 TEAM 记录，删除团队时在一个事务内移除该团队两类记录。

原人员字段通过按记录类型校验的 CHECK 约束继续要求 PERSON 的姓名、账号和通知类型非空。新增部分唯一索引约束每个部门与团队只有一条 TEAM 记录。现有人员主键及通知设置继续保留，任务参数池和执行快照名单继续独立使用。

标准 Maven 测试受现有 POI xslf 依赖缺失阻挡，后端验证临时使用本机已缓存 POI jar。全量前端类型检查存在其他模块的既有错误。MailRecipientDialog 的既有 lint 错误为重复键与未使用变量，页面及 API lint 通过。SkillFlowRecipients 的旧测试有一项失败，使用修改前的 MailRecipientDialog 也复现相同失败。

在当前检出实施，不提交、不部署、不连接业务数据库执行迁移。
